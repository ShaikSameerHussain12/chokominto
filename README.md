# WaterGuard — Water Consumption Fraud Detection & Decision Support System

A full-stack Django application that flags suspicious water consumption accounts for physical inspection, using engineered behavioral features and two supervised classifiers (SVM, KNN). Built as a decision-support tool for utility inspection teams — the system surfaces *candidates for investigation*, it does not make fraud determinations.

> **Read this before the metrics below:** all fraud labels in this project are synthetically generated by a script I wrote (`scripts/generate_demo_data.py`), not observed real-world fraud. See [MODEL_CARD.md](MODEL_CARD.md) for exactly how that works and what it means for the numbers reported here. Short version: this project demonstrates the ML pipeline (feature engineering → training → evaluation → deployment), not validated fraud-detection accuracy.

---

## 1. What this actually does

Water utilities lose revenue two ways: technical loss (pipe leaks, infrastructure failure) and non-technical loss — meter tampering, bypassing, under-reporting. NTL is the harder problem because it looks like normal data unless you know what to look for.

WaterGuard takes monthly consumption readings per customer, engineers 25 behavioral features per account (trend, volatility, seasonality deviation, zero/negative-reading patterns, billing-to-consumption ratios), and trains SVM and KNN classifiers to rank accounts by suspicion score. Utility staff then work through a ranked queue instead of guessing which accounts to physically audit.

## 2. Honest results (run on this repo's own synthetic dataset)

100 synthetic customers, 6,000 cleaned monthly readings, 10 labeled as fraudulent (10%), 80/20 stratified train/test split.

| Model | Accuracy | Precision | Recall | F1 |
|---|---|---|---|---|
| SVM (RBF, balanced) | 0.95 | 1.00 | 0.50 | 0.67 |
| KNN (k=5, distance-weighted) | 1.00 | 1.00 | 1.00 | 1.00 |

**Do not read the KNN row as "the model is perfect."** The test set has 20 customers and only 2 fraud cases in it — at that sample size, one lucky split produces a perfect score without proving anything about generalization. This is flagged in detail in the model card, along with what a defensible evaluation would need (larger dataset, cross-validation, out-of-time validation).

The reference academic project this is loosely modeled on (Yarmouk Water Company, Jordan) reports ~74% SVM / ~70% KNN accuracy on real utility data. That number is *not* this project's result — it's cited in the model card for context only, and the two are not comparable (different data, different label source, different scale).

## 3. Architecture

See [ARCHITECTURE.md](ARCHITECTURE.md) for the full request-flow breakdown. Summary:

- **Backend:** Django 6.1, Python 3.14
- **ML pipeline:** standalone `ml_engine/` package (preprocessing → feature engineering → training → evaluation → visualization), decoupled from Django so it's independently testable
- **Storage:** MySQL via Django ORM, SQLite fallback for local dev
- **Frontend:** Django templates + Chart.js for dashboards, no SPA framework
- **Testing:** pytest / pytest-django

```text
waterguard/
├── config/           # Django settings, URL routing
├── core/              # Models, views, forms, services (orchestration layer)
├── ml_engine/         # Preprocessing, feature engineering, training, evaluation
├── templates/         # Admin portal + customer portal views
├── static/            # CSS
├── data/               # Synthetic datasets
├── models/             # Serialized .joblib model artifacts
├── scripts/            # Synthetic data generator
└── docs/                # Diagrams, report outline
```

## 4. Setup

```bash
pip install -r requirements.txt
cp .env.example .env          # configure DB_ENGINE, or leave blank for SQLite
python manage.py migrate
python scripts/generate_demo_data.py
python manage.py runserver
```

Seed demo accounts from the dashboard's "Seed Demo Dataset" banner after logging in as admin, or:

```bash
python -c "import os, django; os.environ.setdefault('DJANGO_SETTINGS_MODULE','config.settings'); django.setup(); from core.services import seed_demo_data; seed_demo_data()"
```

## 7. Known limitations

- **Labels are self-generated, not observed.** This is the biggest caveat in the project — see the model card.
- **Small sample.** 100 customers is too few to draw statistical conclusions from; it's enough to prove the pipeline works end-to-end.
- **Cold start in production.** A real deployment has no fraud labels at all initially. An unsupervised approach (Isolation Forest, LOF) or manual-audit bootstrapping would be needed before a supervised classifier like this one is usable on real data.
- **No geographic or IoT integration** — batch monthly CSV/DB input only.
